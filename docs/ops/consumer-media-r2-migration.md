# VisuTry Consumer media migration to private R2

## Scope and storage invariants

- Keep Vercel, PostgreSQL, and the existing Cron schedules. The default writer remains Vercel Blob. R2 changes future Consumer Try-On source, item and result images, and Face Analysis source photos. Existing Blob objects, merchant/Store assets, and marketing R2 keep their current locations.
- New R2 values in the server-only media columns are `r2:<key>`. Try-On pins its result backend on task creation. Pre-migration rows stay on their legacy Blob path. Face Analysis preserves its stored provider on completion. Output serializers continue to return app URLs. Owner and admin reads proxy private bytes, and Share serves results only. Face Analysis source reads remain same-origin for Canvas and MediaPipe. Consumer owner/share access ends at business expiry. Store's existing GET-only signed URL remains capped at 120 seconds and clipped to retention.
- Retry and duplicate GrsAi/Kie success observations use the existing DB lease and version. The R2 result key is stable per task, regardless of MIME type. A `412` is reconciled against server-controlled key metadata, and a retry can reconcile a completed write before downloading the vendor result. GrsAi is polled (`webHook: "-1"`); Kie is polled without a callback URL. Stripe callbacks affect entitlement only. The protected-result path also covers manual admin fetch and pending-task Cron.
- Retention is 7/90/365 days. A failed object delete keeps its task and retry state. A denied object request counts as an error. A missing object is handled idempotently. Manual deletes hide media once requested and defer an active R2 writer to Cron. Source writes have a durable staging record generated before upload. Task publication and removal of the staging references use one DB transaction. Failed or ambiguous uploads become eligible for cleanup after one hour via the existing daily Cron. The same Cron records deletion notifications on successful object-and-row cleanup and retries outstanding email. Resend deduplicates the same key for 24 hours. A provider response lost beyond that window has an at-least-once notification tradeoff.
- Keep S3 bucket public access disabled, including the r2.dev URL and custom domains. Use a dedicated private Standard bucket and a bucket-scoped **Object Read & Write** token. Use one bucket per environment, without an automatic object-expiration lifecycle. The endpoint is the account's default-jurisdiction R2 S3 endpoint. R2 credentials stay server-side. [R2 S3 tokens](https://developers.cloudflare.com/r2/api/tokens/) · [R2 conditional writes](https://developers.cloudflare.com/r2/api/s3/conditional-operations/)

## Verify cost in the intended account

1. In Cloudflare, select the account that would own the private bucket. Open **Storage & databases → R2 object storage → Overview**. Use account-wide operation totals for the billing window and check **Billing → Usage** or the current invoice for billable usage. For a reproducible estimate, query `r2OperationsAdaptiveGroups` without a bucket filter using the account tag, group by `actionType` over the current 30-day window, and cross-check the account-level storage snapshot at `GET /accounts/{account_id}/r2/metrics`. Use daily aggregate peak storage across all Standard buckets to estimate GB-month. Bucket Metrics identify which workloads consume the pool. [R2 analytics](https://developers.cloudflare.com/r2/platform/metrics-analytics/) · [Account metrics endpoint](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/metrics/methods/list/)
2. Standard includes 10 GB-month, 1M Class A and 10M Class B operations monthly across the account. Class A includes PUT and LIST. Class B includes GET and HEAD. Deletes and Internet egress have no R2 charge. Retention and traffic affect storage differently from a point-in-time snapshot. Vercel's observed 2,010 advanced operations in 30 days, 1,976 against private Blob, and ~587 MB stored suggest sufficient room if the account has headroom. Vercel's advanced metric and Cloudflare operation classes use different definitions. These figures leave existing data on Blob, and R2 capacity grows as new media accumulates. [R2 pricing](https://developers.cloudflare.com/r2/pricing/)
3. Record aggregate current-month usage from all buckets, including marketing. Start only with at least 20% headroom in each pool after the projected Consumer increase. Set operating thresholds at 70% review and 85% stop expansion. Account headroom needs an account-level reading before rollout.

## Release sequence

| Gate | Action and exit criteria |
| --- | --- |
| Local | Fetch exact `main` and apply the patch. Run TypeScript, Next lint, critical Face Analysis/quota tests, all unit tests, E2E discovery, migration boundary/anchor tests and disposable PostgreSQL contracts. Exercise signed SDK operations using synthetic fixtures, both readers and writer modes, duplicate/late polling, failed uploads before a task or debit, cross-user 403/404, signing expiry, the 7/90/365-day boundaries, cleanup/notification retries, and desktop/mobile behavior. |
| Isolated Preview | Test with an existing private Standard nonproduction bucket and a separate disposable Preview database. Add the four `CONSUMER_MEDIA_R2_*` settings from `.env.example` as Preview-branch-scoped values, plus the write selector and the synthetic canary account. Preserve legacy private Blob fixture access. Use synthetic images and seed the Preview database/R2 fixture objects so that protected media, deletion and retry paths can run with live AI and email credentials absent. Run generation and email mocks in the isolated test process because deployed Preview does not honor the local mock-mode flag. The standard repository ignore-build script skips nonproduction builds, so have the release owner approve a branch-specific manual Preview build or equivalent isolated CI environment and confirm the approved target. Re-run the endpoint matrix below and verify an empty fixture database and bucket prefix at the end. |
| Compatibility release | Following review of the exact commit and intended Vercel project/domain, apply the additive migration via the existing guarded deploy path. Deploy both readers with `CONSUMER_MEDIA_WRITE_PROVIDER=vercel-blob`. Confirm `TRY_ON_BLOB_ACCESS_MODE=private`, `FACE_ANALYSIS_BLOB_ACCESS_MODE=private`, their store IDs and existing private Blob authentication. Save this as the earliest rollback release. Watch a complete 02:00 UTC retention and 03:15 UTC consumer sync cycle before R2 traffic. |
| Canary | When separately authorized and verified, set `CONSUMER_MEDIA_WRITE_PROVIDER=r2` and `CONSUMER_MEDIA_R2_CANARY_USER_IDS` to a comma-separated list of explicit synthetic/internal user IDs. All other users continue writing to private Blob. Complete at least 10 synthetic flows per feature across desktop and mobile, including an old Blob fixture and pending tasks on both providers. Observe one full daily Cron cycle. Require no unauthorized reads, exposed R2 references, duplicate completions/debits, unexplained 403s, or stranded staging/retention work. |
| Switch | Remove the canary restriction after its gate and confirm usage headroom. For the first 72h compare Try-On completion, Face Analysis completion, media 502s, p95 media latency, successful/deferred/failed deletions, queued notifications, and both providers' operation counts to the previous seven days. Roll back for any privacy/quota breach, 3 consecutive storage failures, a media 502 rate at least 1 percentage point above baseline on ≥50 requests, p95 >25% above baseline on ≥50 requests, or any retention item failing two scheduled cleanup runs. |
| Roll back | Set `CONSUMER_MEDIA_WRITE_PROVIDER=vercel-blob` and redeploy the same dual-reader release. Keep both credentials, the additive schema and Cron active. Accepted R2 jobs remain pinned and R2 objects already referenced continue to read/delete. Never restore a pre-dual-reader binary as production after the first R2 write. Verify a new Blob record, an existing R2 result and an in-flight R2 task, plus a cleanup retry. |

## Preview fixture matrix

- Submit Try-On (simple, Compare/Style Explorer and from unlocked Face Analysis Top Picks) and Face Analysis (locked/unlocked). Verify their public DTOs, history, admin detail/fetch, owner media URLs, result-only Share and browser download. Access owner pages as a second account and anonymously. A missing authorized object gives 404, denied S3 access is an upstream failure, and cross-user requests give 403 or concealed 404 per endpoint.
- In synthetic providers, duplicate completed observations around the DB lease, pause before and after PUT then retry, and deliver a late response after deletion was requested. Verify at most one result and one debit, no cross-provider fallback, and no R2 writes for a paused or deleted task. Change writer selection while tasks from both providers are processing. R2 results already written must survive the Blob-write rollback.
- Create synthetic free, credits, and premium fixtures. Test immediately before and at 7/90/365 days by moving fixture dates. Confirm the old Store signed grant is no more than 120 seconds and stops at `expiresAt`, and that Consumer routes do not issue storage grants. Fail DELETE once for each provider, verify the row remains and no notification is sent, then retry across a cleanup run and a simulated failed email. Include owner/admin manual deletion and a source PUT failure before record creation, then verify fixture object, staging and DB removal.
