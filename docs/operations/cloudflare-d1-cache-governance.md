# VisuTry D1 Production Cache Governance Contract

**Status:** repository contract implemented; production hardening not deployed

**Scope:** the existing dashboard-only Cloudflare Cache Rule `VisuTry D1 - SEO HTML Cache Shield`.

This document is the reviewable source of truth for the rule. It does not
change Cloudflare production. The expression and pure eligibility model live in
[`cloudflare-router/d1-cache-governance.ts`](../../cloudflare-router/d1-cache-governance.ts),
and the regression matrix is in
[`tests/unit/cloudflare-d1-cache-governance.test.ts`](../../tests/unit/cloudflare-d1-cache-governance.test.ts).

## Ownership invariant

Vercel is the sole producer of Next HTML, RSC/Flight, and `/_next/static/*`.
D1 may cache only an anonymous document response already produced by Vercel.
It must never become an alternate Next build, RSC/Flight cache, or static asset
owner. This preserves the production invariant that the HTML deployment and
`/_next/static` asset graph have one owner.

## Eligibility contract

The exact proposed expression is generated by the repository module and is
also printable with:

```bash
npm run d1:cache:governance
```

It allows only:

- `www.visutry.com`
- `GET` and `HEAD`
- an empty query string
- no `Cookie` or `Authorization` header at all
- no RSC/Flight or Next navigation headers
- no `Accept: text/x-component`
- no `Purpose` or `Sec-Purpose` containing `prefetch` or `prerender`
- the explicit localized families `/glasses-guide/*`, `/style/*`, and
  `/sunglasses-for/*` for the nine approved locales

Unknown routes, APIs, sitemaps, Store/Campaign paths, and `/_next/static/*`
are outside the rule. Browser caching remains bypassed.

The edge TTL target is **3,600 seconds (1 hour)**. No stale-while-revalidate
behavior is requested. The rule must not rely only on origin `Vary` headers to
protect RSC or prefetch traffic.

## Deployment invalidation contract

After a Vercel Production deployment is verified as `READY` and `PROMOTED`,
purge exactly the 27 family-root URLs plus the 27 trailing-slash HTTPS
prefixes represented by the three D1 families × nine locales. The exact root
URLs are needed because a trailing-slash prefix does not include the root
itself. This is a scoped purge, not a purge of unrelated assets:

- no `/_next/static/*`
- no sitemaps
- no APIs
- no Store/Campaign paths

The executable mechanism is:

```bash
D1_CACHE_PURGE_APPROVED=1 \
CLOUDFLARE_ZONE_ID=... \
CLOUDFLARE_API_TOKEN=... \
VERCEL_PRODUCTION_SHA=... \
VERCEL_PRODUCTION_DEPLOYMENT_ID=... \
npm run d1:cache:governance -- --purge
```

The script fails closed unless all values are present and the explicit
approval variable is `1`. It prints a JSON evidence record containing the
deployment identifiers, exact-file/prefix target count, timestamp, HTTP
status, Cloudflare request ID, and success result; it never prints the API
token.

The repository workflow has no `push` trigger. It accepts only a
`vercel-production-promoted` repository dispatch whose payload proves:
`target=production`, `ready_state=READY`, `ready_substate=PROMOTED`, and
contains both a deployment ID and Git SHA. The external Vercel-to-GitHub
dispatch/webhook wiring is not present in this repository yet, so the
automatic path is not production-ready until that integration and the
dedicated Cloudflare token are provisioned.

Cloudflare documents prefix purge as a supported purge method on all plans,
but the token must have the zone `Cache Purge` permission. The currently used
Wrangler OAuth token does not prove that permission. See the [Cloudflare purge
documentation](https://developers.cloudflare.com/cache/how-to/purge-cache/)
and [purge API reference](https://developers.cloudflare.com/api/resources/cache/methods/purge/).

## Coherence validation before hardening deployment

The deployment review must run the unit matrix and then, in a controlled
read-only probe, verify for one existing URL in each family:

1. Vercel-origin and public response status, content type, canonical, and body
   hash are equal before the rule change.
2. `/_next/static/*` remains Vercel-owned and is not included in any purge.
3. Anonymous queryless HTML may become `HIT` after the first `MISS`.
4. RSC/Flight, prefetch, `Accept: text/x-component`, `Purpose`,
   `Sec-Purpose`, Cookie, Authorization, query-string, and non-GET requests
   remain bypassed.
5. A deployment promotion followed by a successful prefix purge removes the
   old D1-covered HTML before a new response is accepted.
6. A failed purge is visible and blocks the deployment-coherence gate; it is
   never silently treated as success.

The test matrix is automated for the expression/model. Production probes are
required for final rollout because the public edge result cannot be inferred
from the response header observed inside a Worker.

## Rollback

If any hardening check fails, disable the D1 Cache Rule in Cloudflare or
restore the last known-good rule expression. This rollback is independent of
the Vercel application deployment. No Worker route, DNS record, Vercel
setting, or application code change is needed.
